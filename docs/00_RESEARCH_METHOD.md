# 1. Purpose

Этот документ фиксирует метод исследования и принятия продуктовых решений в проекте.

Он отвечает на вопрос: **как мы решаем, что делать и в каком порядке**.

---

# 2. Decision Hierarchy

При принятии любого решения используется следующая иерархия источников:

```text
1. AGENTS.md            — правила работы агента и продукта
2. docs/01_PRODUCT_SPEC — что мы делаем
3. docs/02_ARCHITECTURE — как устроена система
4. docs/03_DATA_API     — контракт данных и API
5. docs/04_RULES        — регламент разработки
6. existing code        — уже реализованное
```

Если документация и код противоречат друг другу — молчаливое изменение запрещено.
Сначала определяется причина конфликта, затем обновляется документация или код.

---

# 3. MVP Research Method

Каждая гипотеза функции проходит минимальную проверку:

```text
Вопрос                             | Источник ответа
-----------------------------------|----------------------------------
Решает ли это проблему пользователя?| 01 §2 Problem, §5 Core Value
Входит ли в MVP?                    | 01 §6, §11, §17; 04 §56
Укладывается ли в архитектуру?      | 02 §4, §27, §32
Есть ли контракт в API?             | 03 §44–45
Безопасно ли?                       | AGENTS §19–20; 04 §48
Как проверить готовность?           | 04 §42 Definition of Done
```

Если функция не отвечает на все вопросы — она откладывается.

# 4. Product Decisions Log

Ключевые зафиксированные решения:

| Решение | Основание |
|---|---|
| GitHub Integration → **разрешена и реализована** (2026-09-16) | Запрет владельца снят: публичный API GitHub как источник данных, без токена и OAuth. Правила в 01 §7 |
| Данные аналитики — только бакеты, без IP и cookie | Приватность посетителей: 03 §11 и `app/utils/analytics.py` |
| Экспорт аккаунта в JSON (`GET /export`) | Read.cv и bento.me закрылись вместе с работами пользователей |
| AI Assistant → POST-MVP | Решение владельца проекта; 04 §57 |
| Таблица Portfolio не создаётся в MVP | 03 §11: portfolio — derived view |
| Поле description не добавляется | Кейс-структура (problem/solution/result) покрывает его |
| Skills формируются из технологий проектов | Нет отдельной сущности Skills в 03 |
| Reorder кнопками вместо drag-n-drop | 04 §45: без лишних зависимостей |
| Локальный Git только как VCS, GitHub как хостинг кода | Решение владельца: продукт не зависит от GitHub |

# 5. Change Protocol

Изменение продукта или архитектуры:

```text
1. Что меняем и почему (какая проблема)
2. Какой документ затрагивается
3. Обновить документацию ПЕРЕД или ВМЕСТЕ с кодом
4. Проверить: тесты, существующая функциональность
5. Понятный commit message
```

---

# 6. Final Rule

> **Делает ли это продукт лучше, полезнее или профессиональнее?**

Если нет — не добавляем.
